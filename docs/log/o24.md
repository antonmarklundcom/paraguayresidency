## Items 1 + 2 — lead delivery queue, WhatsApp lead kind

- `lead_deliveries` (one row per lead × `crm`/`notify`/`autoreply`), opened `pending` before the first attempt,
  then `sent`/`failed`/`dead`/`skipped`. Backoff 1, 5, 30, 120, 360, 1440 min; a 4xx other than 408/429 is
  `dead` at once. Error text is scrubbed of emails and phone numbers before it is stored.
- `runLeadDeliveryQueue()` — due failures, `pending` rows a crashed request left behind (10 min), and on request
  the `skipped` rows (after a CRM key is set). Triggered by `POST /api/leads/deliveries` (bearer
  `LEAD_QUEUE_SECRET`, closed without it), `npm run leads:retry`, and the **Run queue now** button on
  `/admin/leads`, which now also shows queue health, recent failures and per-lead channel status.
- `/api/health` → `leads { queue, lastSuccessAt, failed24h, dead, oldestUndeliveredAt, backlog }`; a backlog over
  an hour sets `degraded`.
- `leads.kind = 'whatsapp'`; `/api/track` + `site_events` for the WhatsApp click beacon; the lead action attaches
  the article slug and the exposed A/B variants server-side. Contract in `docs/conversion-core.md`.
- Migration `drizzle/0002_o24_lead_engine.sql` (not applied). `src/lib/db-features.ts` probes
  `information_schema` so the same code runs on the old schema: WhatsApp leads become `contact` + marker, the queue
  falls back to `crm_status`, clicks are dropped.
- CSV export: cells that would run as a spreadsheet formula get a leading `'` (lead names and messages are typed
  by strangers).
- Tests: `tests/lead-delivery.test.ts` (policy, failing CRM + failing SMTP, migrated vs un-migrated, queue),

## Items 3 + 10 — attribution and the A/B hook

- `src/proxy.ts` now writes the first-touch cookie `vc_attr` (http-only, 90 days) on the first page view that
  carries UTM/click ids or an outside referrer (`src/lib/first-touch.ts`), and assigns `ab_<experiment>` server-side
  for the brands an experiment runs on (`src/lib/experiments.ts`). A response that sets a cookie goes out
  `private, no-store` so a shared cache never replays one visitor's cookie to another.

  only exposed variants. JS off → control, not counted.
- `/admin/attribution` (hub only): leads by brand, kind, first-touch source, form page and landing page (7/30 days),
  WhatsApp clicks by page and source, the A/B readout with a "not enough data yet" floor of 30 leads per variant, and
  a 30-day attribution CSV (lead id, no contact details).
- Tests: `tests/attribution-report.test.ts`, including a round trip of the proxy's real `Set-Cookie` through Next's
  cookie reader into `parseAttribution`. Checked in a production build: a new hub visitor with `?utm_source=` gets
  `vc_attr` (HttpOnly) + `ab_hero_cta` and `cache-control: private, no-store`; a returning visitor gets no cookie and
  the normal ISR `s-maxage=600`. Seven-host smoke still green.
- DB work: none (existing `leads.attribution` JSON and the 0002 `site_events` table).

## Hotfix — Hostinger build (Turbopack → webpack)

Hostinger's build of `67c5007` failed: `TurbopackInternalError … src/app/globals.css … node process exited before
we could connect to it`. Turbopack evaluates PostCSS in child Node processes it spawns; on the shared build box
they die before connecting (the account's process/thread cap — the reason `experimental.cpus: 1` exists — does not
govern Turbopack's own workers). CI and local builds were green, which is why nothing caught it.

- `npm run build` is now `next build --webpack` (PostCSS in-process, one build worker).
- Switching surfaced a real bug Turbopack had tolerated: three client form components imported the field names
  from `form-guard.ts`, which pulls `node:crypto` (`signing.ts`) into the browser graph. The names now live in
  `src/lib/form-fields.ts`; `form-guard.ts` re-exports them.
- Checked: `npm run verify` (webpack build), seven-host smoke with all 358 sitemap URLs 200, `tests/abuse.mjs`
  all probes pass, no server errors logged.
