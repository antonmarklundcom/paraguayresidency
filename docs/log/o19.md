**2026-09-15 — O19 Rendering & LeadForm performance (Opus, run by a Sonnet manager/Codex worker session)** — PR: https://github.com/antonmarklundcom/paraguayresidency/pull/32

What now exists: every `src/app/sites/<key>/` folder moved to `src/app/(<locale>)/sites/<key>/` (en/es/pt/sv route groups), replacing the single `headers()`-reading root layout with four independent root layouts, each with a hardcoded `<html lang>` — this is what makes static generation possible at all. A clean build now shows 128 of 157 real `sites/**` routes as static (104 fully static, 24 static with generated params) = 81.5%, clearing the plan's ≥80% bar; the remaining 29 are exactly the plan's named exceptions (confirm/route-finder-result/unsubscribe per brand, guide's member area). LeadForm, NewsletterForm and MagicLinkForm each got a server-rendered base (`<form action={serverAction}>`, country `<select>` options rendered server-side, no `COUNTRIES` in the client bundle) that submits and redirects correctly with zero JavaScript, plus a lazy client enhancement (`ProgressiveForm` + `FormEnhancement`, triggered by scroll-into-view or focus) that swaps in the richer `useActionState` experience without losing what the visitor already typed. A new `whatsapp` lead variant (name + WhatsApp number + one line, no email) is available — not yet wired into any page, that is a later phase's job. `src/lib/analytics.tsx` (ported from S6's still-unmerged branch) exposes `track(name, props)`, wired into `lead_submitted`, `newsletter_subscribed`, `checkout_started`, `quiz_completed` — no PII in any event's properties. `tests/lighthouse.mjs` runs a real mobile Lighthouse audit via Playwright's own bundled Chromium against the seven brand homes plus three extra pages; every page clears the 0.90 bar, most at a perfect 1.00. 469 tests, was 437.

Two real bugs found and fixed along the way, neither anticipated by the plan: `next-mdx-remote` v6 defaults to `blockJS: true`, which silently strips expression-valued JSX props (like `<StatRow stats={[...]}>`'s literal array) — set `blockJS: false, blockDangerousJS: true` instead, independent of the route-group work that happened to expose it. And a genuine npm dependency-resolution bug: `vite@8.3.0`'s peer want of `esbuild ^0.27.0 || ^0.28.0` was getting incorrectly deduped to an incompatible `0.25.12` (pulled in by `drizzle-kit`'s own separate `^0.25.4` need), which `npm ci` tolerates locally on Windows but hard-fails on Linux CI with `EBADPLATFORM` once the two eventual devDependency additions (`lighthouse`, `playwright`) changed the tree shape enough to surface it. Fixed with a scoped `overrides` entry forcing `vite`'s (and `vitest`'s) esbuild to `^0.28.0`, plus a direct patch to ~26 lockfile entries npm's own writer left marked `extraneous` instead of `optional` — confirmed this npm bug reproduces deterministically across multiple from-scratch reinstalls, not caching noise.

Decisions and deviations:
- The success/error confirmation after a no-JS form redirect is read entirely client-side (`window.location.search` via `useSyncExternalStore`), never through a server Component `searchParams` prop — reading `searchParams` on a marketing page would have forced it back to dynamic rendering and undone the static-conversion work. A visitor with JavaScript fully disabled sees the blank form again after a successful submission rather than a confirmation banner; their data is saved regardless. Accepted trade-off, not a bug to chase further.
- The four group-level `not-found.tsx` files (one per locale) no longer call `currentSite()`/`headers()` — every known site's 404 is handled by its own per-site `not-found.tsx`, so the group-level ones only ever fire for a request matching no known site at all and can use a hardcoded default (`HUB_SITE` for `(en)`, the single brand for `(es)/(pt)/(sv)`).
- `src/lib/analytics.tsx` duplicates S6's still-unmerged `Analytics` component verbatim; per S6's own note in `docs/runbook.md`, S6's version wins on merge and this becomes a straightforward concatenation, not a conflict.

Pre-handoff audit (§4.9): `npm run verify` re-run green (469 tests); every commit was independently re-verified by actually running the build/tests/typecheck rather than trusting the worker's own report, catching one real double-`SiteShell`-chrome bug in an intermediate not-found.tsx draft before it shipped, and the two dependency bugs above (both confirmed via real GitHub Actions CI runs, not just local reproduction).
