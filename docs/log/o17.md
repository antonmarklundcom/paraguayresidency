What now exists: every P0 and P1 in `docs/improvement-report.md` §1 items 1–6 and 10 is fixed, each with a named test; 395 tests, was 322. `finishWebhookEvent` writes `processed_at` only on success (`webhookClosure`), so a failed delivery's retry re-runs instead of answering `duplicate:true`; both webhook routes hold `withEventLock` from the idempotency insert to the close-out, and `fulfilCheckout` claims with `UPDATE … WHERE status <> 'paid'` whose affected-row count gates the token, the receipt and the sign-in link. `signingSecret()` throws `WeakSecretError` in production when `SESSION_SECRET` is missing or under 32 chars — request-time, so `next build` and `npm run verify` still pass with an empty `.env` — and `/api/health` reports `secret: "ok"|"weak"`. `order_refunded` is handled; `effectiveTier` grants `entry` only for a subscription that had a paid period (`subscriptionEverPaid`, no new column); `grantTierUntil` writes real `subscriptions`/`purchases` rows marked `admin_grant_…` instead of the cache; `FREE_ACCESS_MODE` gives each free purchase a unique `provider_order_id`, refuses to run beside a live `STRIPE_SECRET_KEY` and is capped at 5/hour/IP; the member resource download runs the same `isUnlocked()` as the lesson pages. New `src/lib/rate-limit.ts` — `take(key, max, windowMs)` over a Map, lazy per-key eviction, deliberately no global `clear()`.

The Lemon Squeezy retry finding (the one thing O18/O19 should not re-derive): `docs.lemonsqueezy.com` is blocked from this container; from their published webhook docs and their own `lemonsqueezy.js` types, LS retries a non-200 up to three more times with exponential backoff (~5 s / 25 s / 125 s) and re-sends the **same signed bytes**, and there is **no documented per-delivery id** — `meta.webhook_id` names the webhook ENDPOINT, not the delivery. So §14.1.4's suggested "prefer `meta.webhook_id`" is NOT implemented: keying on it would collapse every event from one endpoint into a single `webhook_events` row and drop every purchase after the first. The key is `<event_name>:<data.id>:<sha256(raw body)>` in all cases — retry-stable and distinct per real event. Reasoning is in the comment above `lemonSqueezyEventId`.

Decisions and deviations:
- **One documented exception to the weak-secret refusal:** the purpose `form-timestamp`. The forms' anti-bot render timestamp is friction, not a boundary, and throwing for it would 500 every marketing page carrying a `<LeadForm>` and break `next build` once O19 prerenders them. `signingSecret(purpose)` takes a one-entry allowlist; everything that grants something (sessions, magic links, unsubscribe and download tokens) is absent from it and throws. The allowlist lives in `signing.ts`, so `src/lib/form-guard.ts` — O18's file — was not touched.
- A dated **`entry`** admin grant is refused with a message saying what to do instead (grant `insider` until that date), because a purchase has no expiry column and the schema is FINAL. `KNOWN-ISSUES.md` + Backlog `purchases.expires_at`.
- `resources` has no `drip_days`, so `resourceUnlocked()` passes a documented constant 0 — the route runs the full gate, so the column is one constant away. Backlog.
- Every test is pure or in-memory, as §14.1.8 requires. What that does NOT cover is the SQL under the decisions (`affectedRows` on a re-claim, `ER_DUP_ENTRY` on `purchases_checkout_uq`); logged as an open item in `KNOWN-ISSUES.md` and the Backlog.
